## ADDED Requirements

### Requirement: Единый конвейер путей обновления (верхний уровень — частный случай)
Если тип помечен атрибутом `ExtendedWith`, система SHALL строить **все допустимые пути обновления** как последовательности имён свойств от корневого типа до цели (leaf или вложенный record-узел), используя **один и тот же** алгоритм перечисления и генерации для любой длины пути.

- Путь длины **1** (одно свойство корня) SHALL трактоваться как обычный “верхний” `With_<Property>` без отдельной ветки генератора.
- Пути длины **≥ 2** SHALL давать “вложенные” имена `With_<Seg1>_<Seg2>_...` по тем же правилам именования и перегрузок.

#### Scenario: Один алгоритм для корня и вложенности
- **WHEN** система генерирует методы для свойства `Name` (не record) и для пути `A.B.X` (leaf)
- **THEN** оба семейства методов MUST происходить из одного конвейера (перечисление путей → выбор семантики null → эмиссия перегрузок), без дублирующей логики “только для первого уровня”.

### Requirement: Генерация путевых `With_` методов для record-свойств
Если тип помечен атрибутом `ExtendedWith`, система SHALL генерировать extension-методы для обновления целей, достижимых по путям через свойства, тип которых на промежуточных сегментах является `record` (см. правила leaf/record-узла в design).

#### Scenario: Генерация для 1 уровня вложенности
- **WHEN** у типа с `ExtendedWith` есть свойство `Address`, и его тип является `record`, и у `Address` есть leaf-свойство `City`
- **THEN** система MUST сгенерировать **семейство** методов `With_Address_City` с **полным набором перегрузок** (см. requirement ниже), аналогичным “верхнему” `With_<Property>` для того же leaf-типа

#### Scenario: Генерация для нескольких уровней вложенности
- **WHEN** у типа с `ExtendedWith` есть свойство `A` (record), у `A` есть свойство `B` (record), у `B` есть leaf-свойство `X`
- **THEN** система MUST сгенерировать **семейство** `With_A_B_X` с тем же полным набором перегрузок, что и для односегментного пути той же глубины nullability

### Requirement: Полный набор перегрузок (8) для каждого семейства пути
Для каждого сгенерированного **базового** имени метода по пути (например `With_A_B_Leaf`, или `TryWith_...` / `With_..._OrThrow` при nullable-сегментах) система MUST генерировать **ровно восемь** перегрузок, совпадающих по **форме** с перегрузками односегментного `With_<Property>` для того же типа leaf (или целевого record-узла, если путь заканчивается record):

1. `(..., <TargetType> newValue)` — синхронное значение, приёмник `this <Root>`
2. `(..., Task<TargetType> newValueTask)` — значение из задачи, приёмник `this <Root>`
3. `(..., Func<TargetType, TargetType> updateValueFunc)` — синхронная функция от текущего значения, приёмник `this <Root>`
4. `(..., Func<TargetType, Task<TargetType>> updateValueFunc)` — асинхронная функция, приёмник `this <Root>`
5. — те же четыре варианта с приёмником `this Task<Root>` (методы остаются `async`, возвращают `Task<Root>`).

`TargetType` — тип обновляемого leaf либо тип record-узла на конце пути, если генерируется обновление целого вложенного record (как в существующей модели путей).

#### Scenario: Вложенный путь имеет столько же форм перегрузок, сколько верхний `With_`
- **WHEN** для корня уже принят набор из восьми перегрузок для `With_SomeLeaf`
- **THEN** для пути `A.B.SomeLeaf` система MUST предоставить восемь перегрузок с теми же комбинациями (значение / `Task<>` / синхронный `Func` / асинхронный `Func` × `this Root` / `this Task<Root>`), отличаясь только именем метода и телом обхода пути

### Requirement: `NoNestedWith` отключает вложенную генерацию, но не верхний `With_`
Если на свойстве указан атрибут `NoNestedWith`, система MUST трактовать его как запрет **углубления в детей** этого свойства при построении путей (т.е. не генерировать методы для `Prop.*`, `Prop.*.*`, ...), но MUST продолжать генерировать методы для **самого свойства `Prop`** как цели пути — независимо от того, находится ли `Prop` на корне или глубже в пути.

Если `NoNestedWith` указан на свойстве, которое **не является record**, его применение является семантически бессмысленным и MUST NOT влиять на генерацию (т.е. метод для этого leaf-свойства всё равно генерируется по общим правилам).

Если требуется отключить генерацию `With_<Property>` для самого свойства, пользователь SHALL использовать `ExtendedWithIgnoreAttribute`.

#### Scenario: `NoNestedWith` на record-сегменте
- **WHEN** свойство `A` помечено `NoNestedWith`, и тип `A` является `record`, и внутри `A` есть leaf-свойство `X`
- **THEN** система MUST не генерировать методы вида `With_A_...` / `TryWith_A_...` / `With_A_..._OrThrow` для leaf-свойств внутри `A`, но MUST продолжать генерировать метод для самого свойства `A` (например `With_A(...)` на соответствующем уровне пути)

#### Scenario: `NoNestedWith` на leaf-свойстве не влияет на генерацию
- **WHEN** leaf-свойство на пути (не record) помечено `NoNestedWith`
- **THEN** система MUST продолжать генерировать методы для пути, заканчивающегося на это leaf-свойство, так же, как если бы атрибута не было

### Requirement: Промежуточные методы для префиксов пути
Если система генерирует семейство методов для полного пути вида `With_A_B_Leaf`, она MUST также генерировать **семейства** (с полным набором перегрузок) для каждого допустимого record-префикса этого пути (если не отключено `NoNestedWith` и нет коллизии по имени/сигнатуре), например:
- `With_A` (если цель — обновление `A` как record-узла на этом префиксе)
- `With_A_B` (аналогично для префикса `A.B`)

#### Scenario: Генерация методов для префиксов пути
- **WHEN** система генерирует `With_A_B_Leaf` (все 8 перегрузок)
- **THEN** система MUST также предоставить по 8 перегрузок для `With_A` и `With_A_B` там, где эти пути сами являются допустимыми целями генерации

### Requirement: Перегрузки с делегатами для leaf (и симметрия с `Task<>`)
Семейство из восьми перегрузок SHALL включать синхронный и асинхронный `Func` от текущего значения цели (см. requirement «Полный набор перегрузок»), с той же семантикой, что и у односегментного `With_<Property>`.

#### Scenario: Обновление leaf по текущему значению
- **WHEN** вызывается `With_A_B_X(source, x => x + 1)` для leaf типа `int`
- **THEN** система MUST вычислить новое leaf-значение на основе текущего значения по пути `A.B` и применить его так же, как value-вариант с вычисленным значением

#### Scenario: Асинхронное обновление leaf
- **WHEN** вызывается перегрузка с `Func<LeafType, Task<LeafType>>` на вложенном пути
- **THEN** система MUST дождаться результата делегата и подставить его как новое значение leaf, согласованно с перегрузкой `Task<>` приёмника корня

### Requirement: Семантика обновления через value-copy (`with`)
Сгенерированные вложенные методы MUST возвращать новый экземпляр исходного типа, обновляя значения по пути через копирование `record` с использованием `with` (или эквивалентного механизма, обеспечивающего value-обновление без мутации).

#### Scenario: Обновление leaf-свойства
- **WHEN** вызывается `With_A_B_X(source, newValue)`
- **THEN** возвращаемое значение MUST быть эквивалентно обновлению `source` таким образом, что меняется только `X` во вложенном record по пути `A.B`, а остальные значения сохраняются

### Requirement: Определение record-типа
Система MUST определять record-тип через Roslyn-семантику (`IsRecord == true`) с учётом nullable-обёртки (т.е. для `R?` underlying тип — `R`).

#### Scenario: Nullable record-тип распознаётся как record
- **WHEN** свойство имеет тип `SomeRecord?`
- **THEN** система MUST рассматривать underlying тип как `record` для целей проверки типа

### Requirement: Защита от циклов типов
Система MUST предотвращать бесконечную генерацию путей при циклах в графе record-типов, используя детекцию повторного посещения типа, и MUST прекращать углубление в циклический сегмент.

#### Scenario: Самоссылочный record
- **WHEN** record-тип содержит свойство, которое (прямо или косвенно) возвращает к уже посещённому record-типу
- **THEN** система MUST не генерировать методы для путей, требующих повторного захода в уже посещённый тип

### Requirement: Nullable сегменты по пути — два семейства по 8 перегрузок
Если на пути к цели есть хотя бы один nullable record-сегмент (`R?`), система MUST генерировать **два** семейства методов, **каждое** с **полным набором из восьми перегрузок** (те же формы, что у `With_<path>` без nullable-сегментов):

- `TryWith_<path>(...)` — семантика **null propagation** на каждом nullable record-сегменте
- `With_<path>_OrThrow(...)` — семантика **явного исключения** при `null` на таком сегменте

Пути **без** nullable record-сегментов SHALL получать только семейство `With_<path>` (8 перегрузок), без дублирования `TryWith_` / `_OrThrow`.

#### Scenario: Null propagation — встретился null по пути
- **WHEN** вызывается любая перегрузка `TryWith_A_B_X(...)` и на некотором nullable-сегменте пути фактическое значение равно `null`
- **THEN** система MUST вернуть исходный корневой экземпляр без изменений (для приёмника `Task<Root>` — после получения корня из задачи, без обновления вложенного пути)

#### Scenario: Throw — встретился null по пути с явным сообщением
- **WHEN** вызывается любая перегрузка `With_A_B_X_OrThrow(...)` и на nullable record-сегменте фактическое значение равно `null`
- **THEN** система MUST выполнить **`throw new NullReferenceException(<message>)`** (не полагаться на неявное разыменование без сообщения)
- **AND** текст `message` MUST быть достаточно информативным для отладки: как минимум префикс идентификатора продукта/генератора (например `Withat:`), **имя сегмента**, на котором остановились, **и/или** префикс пути свойствами (например `A.B`), а также однозначная связь с именем вызываемого метода

#### Scenario: Имена методов позволяют выбрать семантику
- **WHEN** путь содержит nullable record-сегмент
- **THEN** система MUST предоставить оба семейства с различающимися базовыми именами (`TryWith_<path>` и `With_<path>_OrThrow`), каждое с восьмью перегрузками

#### Scenario: Null guard не применяется к цели пути — только к traversal-узлам
- **WHEN** вызывается func-перегрузка `TryWith_<path>(Func<T, T>)` и последний сегмент пути (цель) является nullable record со значением `null`, а все предшествующие traversal-узлы ненулевые
- **THEN** система MUST вызвать переданную функцию с `null` в качестве аргумента и применить возвращённое значение как новое значение цели (null propagation НЕ срабатывает)
- **AND** аналогичное поведение MUST быть у `With_<path>_OrThrow`: при null-цели исключение не бросается, функция вызывается с `null`

### Requirement: Коллизии имён из-за неоднозначного `PathSuffix`
Если **какие-либо два разных допустимых пути** обновления приводят к одному и тому же **базовому имени метода** `With_...` / `TryWith_...` / `With_..._OrThrow` (т.е. имя семейства совпадает при построении из `PathSuffix`), система MUST бросить исключение и прекратить генерацию для этого record-типа.

При этом **сигнатуры/типы параметров не учитываются**: даже если C# мог бы разрешить перегрузку по типам, это всё равно считается неоднозначностью именования и MUST приводить к ошибке.

#### Scenario: Неоднозначность имени `A_B` vs `A.B`
- **WHEN** сгенерированные пути `A.B.<LeafOrTarget>` и `A_B.<LeafOrTarget>` (для одного и того же record-типа и соответствующего leaf/target в конце пути) дают одно и то же базовое имя семейства `With_<...>`
- **THEN** система MUST бросить исключение (например `InvalidOperationException`) с сообщением, содержащим как минимум базовое имя метода и оба неоднозначных пути
