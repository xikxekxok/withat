## Context

Сейчас генератор расширений `With_` работает только на уровне "верхних" свойств типа, помеченного атрибутом `ExtendedWith`. При этом в доменной модели широко используются композиции через `record`-типы (вложенные value-объекты). Из-за отсутствия вложенных `With_` методов потребителю приходится вручную создавать новые значения вложенных record, даже если меняется одна простая "листьевая" характеристика.

Ограничения/ожидания:
- Генерация выполняется через source generator, значит важны стабильность имён, предсказуемость и ограничение взрывного роста количества методов.
- `record` в C# задаёт семантику value-объекта, поэтому "вложенное обновление" должно выражаться как создание нового значения (через `with`/копирование), а не мутация.

## Goals / Non-Goals

**Goals:**
- Генерировать путевые `With_` методы для всех допустимых путей (включая односегментные и вложенные через `record`-свойства).
- Поддержать произвольную вложенность record-свойств с защитой от циклов типов.
- Сохранить и **распространить** эргономику текущего API: для каждого пути — те же **восемь** перегрузок, что у `With_<Property>`; имена вложенных путей — `With_<Seg1>_<Seg2>_...`.
- Определить чёткие правила включения/исключения свойств, обработку `null`/nullable (`TryWith_` / `_OrThrow` × 8), явные сообщения при throw и строгую обработку коллизий базового имени метода, возникающих из-за неоднозначного `PathSuffix`.

**Non-Goals:**
- Не меняем **ожидаемую форму** публичного API для односегментного `With_<Property>`: тот же набор из восьми перегрузок и та же семантика; реализация может быть переведена на общий конвейер путей (путь длины 1 — частный случай).
- Не вводим runtime-рефлексию или зависимость от внешних библиотек.
- Не пытаемся "достраивать" экземпляры `record` при отсутствии значения (например, не создаём `new()` автоматически).

## Decisions

### 1) Что считать `record` типом

**Decision:** свойство считается "record-typed", если его тип в Roslyn является `INamedTypeSymbol` с `IsRecord == true`. Для nullable (`R?`) используется underlying тип `R`.

**Rationale:** это корректно отражает семантику C# `record` и не требует эвристик по синтаксису.

**Alternatives considered:**
- Эвристика по наличию `with`-поддержки/`Clone` → менее надёжно и сложнее.

### 2) Какие методы генерировать (форма API) и единый конвейер

**Decision:** один конвейер **перечисление путей → эмиссия методов** для всех допустимых длин пути. Корневое свойство (путь из одного сегмента) не обрабатывается отдельным генератором: это тот же путь, что и префикс многосегментного.

Для пути `Outer.PropA (record) -> PropB (record) -> Leaf` базовое имя: `With_PropA_PropB_Leaf`. Для **каждого** такого базового имени (а также `TryWith_...` / `With_..._OrThrow` при nullable record-сегментах) генерируется **ровно 8 перегрузок**, изоморфных набору для односегментного `With_Leaf`:

- синхронное значение, `Task<>` значения, синхронный `Func`, асинхронный `Func` (`Task<>` результата);
- те же четыре формы с приёмником `this Task<Outer>` и `async`/`Task<Outer>` возвратом.

Тело метода выражает обход пути и пересборку через `with` без мутации исходного экземпляра.

**Rationale:** одинаковая эргономика для "первого" и вложенных уровней; предсказуемое число перегрузок на путь; проще сопровождать один кодоген.

**Alternatives considered:**
- Отдельная генерация только для верхнего уровня и упрощённые 1–2 перегрузки для вложенных путей → фрагментированный API и дублирование логики.
- `With_PropA(this Outer, Func<PropAType, PropAType> update)` как единственная форма → гибко, но хуже discoverability.
- Генерация только 1 уровня вложенности → не покрывает типичные многоуровневые value-объекты.

### 3) Глубина рекурсии и защита от циклов

**Decision:**
- Рекурсия по record-свойствам выполняется до листьев, но с защитой от циклов типов по набору `visited` (по `ITypeSymbol`).
- Если обнаружен цикл (тип уже в `visited`), углубление в этот тип прекращается (методы для более глубоких путей не генерируются).

**Rationale:** предотвращает бесконечные графы при самоссылках и взаимных ссылках record-типов.

### 4) Какие свойства включать в генерацию

**Decision:**
- В путях учитываются только public instance свойства:
  - доступные для чтения,
  - и доступные для инициализации через `with` (т.е. имеющие `init` или setter, совместимый с `with`-копированием record).
- Если на свойстве указан атрибут `NoNestedWith`, то это свойство исключается из построения путей для вложенных методов (как record-сегмент и как leaf).
- Исключаются индексаторы и свойства без имени (служебные).
- Для leaf-свойств допускаются как record, так и не-record типы, но генерация путевого метода создаётся только для leaf, который НЕ является record (иначе leaf не лист).

**Rationale:** метод должен компилироваться и реально обновлять значение через `with`. Индексаторы/закрытые сеттеры почти всегда ведут к некомпилируемому коду.

### 5) Nullability / `null` значения по пути

**Decision:**
- Если по пути встречается nullable record-сегмент (`R?`), генератор создаёт **два семейства**, каждое с **восемью перегрузками**:
  - **Null propagation**: `TryWith_<path>(...)` — на любом nullable record-сегменте при `null` возвращается исходный корень без изменений.
  - **Throw**: `With_<path>_OrThrow(...)` — при `null` на таком сегменте выполняется **`throw new NullReferenceException(message)`** с явным текстом (не полагаться только на неявное разыменование). Сообщение SHOULD включать префикс продукта (например `Withat:`), имя проблемного сегмента, префикс пути свойств и связь с отображаемым именем метода — для упрощения отладки.

Если nullable record-сегментов на пути нет, генерируется только `With_<path>` (8 перегрузок).

**Null guard применяется только к traversal-узлам, но НЕ к цели пути:**
Последний сегмент пути является **целью** обновления — его текущее значение не имеет значения для guard-логики:
- для value-перегрузок оно просто заменяется;
- для func-перегрузок оно передаётся в функцию как аргумент (включая `null`, если тип nullable).

Null guard на цели был бы ошибкой: он блокировал бы запись нового значения в поле, которое ещё не инициализировано (равно `null`), и предотвращал бы вызов функции с текущим состоянием цели.

**Rationale:** явный выбор семантики по имени; одинаковая мощность API для безопасного и строгого вариантов; осмысленное сообщение при `_OrThrow` дешевле диагностики, чем "голый" NRE.

**Alternatives considered:**
- Factory-параметр при `null` → раздувание сигнатур.
- Throw как единственное поведение → хуже DX, когда нужна осторожная семантика.
- Null guard на цели для func-перегрузок → блокирует легитимный сценарий инициализации null-поля через функцию.

### 6) Коллизии имён и предсказуемость

**Decision:**
- Имя метода формируется строго как `With_` / `TryWith_` / `With_..._OrThrow` + сегменты пути, соединённые `_` (без изменения регистра имён свойств).
- Коллизия обрабатывается строго по **базовому имени семейства** (т.е. по имени, которое получается из `PathSuffix`): если два разных допустимых пути порождают одно и то же базовое имя семейства `With_...` / `TryWith_...` / `With_..._OrThrow`, генератор MUST бросить исключение и прекратить генерацию для данного record-типа.

**Rationale:** неоднозначное именование делает сгенерированный API непредсказуемым (часть семейств может соответствовать разным путям), поэтому генерация должна завершаться ошибкой на этапе компиляции.

## Risks / Trade-offs

- **[Рост количества методов]** → Mitigation: защита от циклов; восемь перегрузок на семейство (и ×2 при nullable-сегментах); ограничение только public/init-able свойств.
- **[Не покрываем nullable record-свойства]** → Mitigation: явное правило в spec; при необходимости позже можно расширить capability с factory/делегатами.
- **[Сложность проверки "init-able"]** → Mitigation: опираться на Roslyn-семантику record `with` и доступность сеттера/`init`, покрыть тестами.
